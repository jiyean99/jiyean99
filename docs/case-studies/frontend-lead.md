# 프론트엔드 리드 · 기능 기획

> **Case Study** · 디자인팀 소속 · 전사
> 만드는 일 옆에서 **무엇을 만들지 정하는 일**을 함께한 기록

[`← 경력 상세로`](../experience.md)

---

## A. Executive Summary

디자인팀 소속으로 합류해 프론트엔드 개발과 **프로젝트 리드**로 역할을 확장한 영역입니다. 개발 외에 디자인 시안·기능 기획·조직 커뮤니케이션까지 담당했습니다.

이 케이스의 핵심은 **"기획 → 시안 → 구현 → QA를 같은 사람이 수행하면 무엇이 달라지는가"**입니다. 사이에서 사라지는 것이 없다는 게 가장 큰 장점이었고, 대신 **결정을 기록으로 남기는 일**이 훨씬 중요해졌습니다. 혼자 아는 것은 조직에 남지 않기 때문입니다.

## 02. Problem - 이 역할이 왜 필요했는가

```text
현재 상황
  기획은 기획팀이, 디자인은 디자인팀이, 구현은 개발이 나눠서 한다

      ↓
문제
  기획 의도가 시안에서 한 번, 구현에서 또 한 번 손실된다
  그리고 구현 난이도가 시안이 확정된 뒤에야 드러난다

      ↓
원인
  단계 사이의 전달이 문서로만 이뤄지고, 각 단계가 다음 단계의 제약을 모른다

      ↓
비즈니스 영향
  구현 중 되돌리는 일이 잦고, 그 비용이 가장 크다

      ↓
해결 방향
  단계를 한 사람 안에서 잇고, 대신 결정을 기록으로 남긴다
```

## 03. 기능 기획 - 무엇을 만들지 정하는 자리

개발 범위와 화면 시나리오를 직접 정의했습니다. 실제로 작성한 기획서입니다.

| 기획서 | 시점 |
|---|---|
| 경기결과 페이지 → **Score 페이지 개선** | 2025.03 |
| 나도 승부사 - **분석글 삭제·수정 기능 추가** | 2023.11 |
| 대시보드 팝업 - 스포츠 이슈·추천 분석글 **타이틀 출력 조건 수정** | 2025.08 |
| **베팅내역 공유 채팅 - 스포츠톡 자동 업로드** | 2025.02 |
| **스포츠 이슈 이미지·URL 팝업 스와이프** | 2025.01 |
| 프리미엄 분석가·나도 승부사 페이지 **띠배너** | 2025.04 |

### 기획서에 반드시 넣은 것

```text
화면 정의 · 사용자 흐름 · 예외 케이스 · 데이터 요구사항
```

**예외 케이스와 데이터 요구사항을 넣은 이유** - 이 둘이 빠진 기획서는 구현 단계에서 반드시 되돌아옵니다. "이 목록이 비어 있으면 뭘 보여주나요", "이 값은 어디서 오나요"를 착수 전에 좁히는 것이 제 역할이라고 봤습니다.

> 💡 **만들지 않기로 하는 판단도 함께 했습니다.** 무엇을 만들지 정하는 자리에 있다는 건, 요청을 그대로 티켓으로 옮기지 않는다는 뜻이기도 합니다.

## 04. 디자인 시안 · 구현

- **Adobe XD로 시안 직접 제작** - 승부사 온라인 배너(v1.3) · 페이지별 화면 정의(v1.3) · 아이콘 세트
- 디자인–구현이 한 사람 안에서 이어지므로 **시안 단계에서 구현 난이도를 미리 반영**
- 반응형·애니메이션을 담당하며 PC·모바일 렌더링 차이를 흡수

```text
Decision   시안 단계에서 구현 난이도를 반영해 미리 조정
Reason     확정된 시안을 구현 중에 되돌리는 비용이 가장 크다
Trade-off  디자인의 이상적인 형태를 일부 포기하게 된다
```

## 05. 기술 트렌드 조사 · 사내 발표

| 시점 | 주제 |
|---|---|
| 2023 | 웹 / UI 트렌드 |
| 2024 상반기 | CSS 신규 명세·기법 |
| 2024 하반기 | Lottie |
| 2025 | UX/UI + 프론트엔드 |

**조사로 끝내지 않는 것을 원칙으로 했습니다.** Lottie 조사는 실제 서비스의 적용 사례를 화면 단위로 분석해 **도입 기준을 제시**하는 형태로 정리했습니다. "이런 게 있다"가 아니라 "우리 서비스의 이 화면에 쓰면 이런 이득과 이런 비용이 있다"까지 가야 조사가 의사결정에 쓰입니다.

## 06. 팀 커뮤니케이션 · 지식 축적

- **2023.04부터 2년 이상 매주** 디자인팀 주간 이슈 자료를 직접 작성·공유
- 진행 중 이슈 · 기기별 렌더링 문제 · 프론트엔드 규칙 변경을 **팀 공통 지식으로 축적**
- **인수인계 문서(문서 + 체크리스트)**를 작성해 담당 영역·규칙·주의사항을 이관

### 왜 매주 썼는가

혼자 담당하는 영역이 넓을수록 **"저 사람만 아는 것"이 늘어납니다.** 그게 조직의 리스크입니다. 매주 쓰는 자료는 그 리스크를 조금씩 덜어내는 장치였습니다.

특히 **기기별 렌더링 문제**는 한 번 겪고 잊으면 다음에 또 반나절을 씁니다. 기록해두면 팀의 자산이 됩니다.

## 07. 공용 규칙 정리

프론트엔드 리드로서 화면이 늘어도 톤이 흐트러지지 않도록 규칙을 문서화했습니다.

| 규칙 | 목적 |
|---|---|
| 공용 스타일 · 컴포넌트 규칙 | 화면이 늘어도 일관성 유지 |
| 반응형 · 접근성 기준 | 기기별 대응을 매번 다시 판단하지 않기 |

## 29. Reflection

### 무엇을 잘했는가

**단계 사이의 손실을 없앴습니다.** 기획 → 시안 → 구현 → QA를 같은 사람이 수행하면 "기획 의도가 뭐였죠?"라는 질문 자체가 생기지 않습니다.

**조사를 의사결정 형태로 변환했습니다.** 트렌드 발표가 정보 공유로 끝나면 아무것도 바뀌지 않습니다.

**매주 썼습니다.** 2년 이상 이어간 것이 이 역할에서 가장 실질적인 기여였다고 생각합니다.

### 무엇이 부족했는가

**한 사람 안에서 끝나는 구조의 위험을 늦게 인식했습니다.** 사이에서 사라지는 게 없다는 장점의 이면은, **검증하는 사람도 없다**는 것입니다. 기획 의도가 잘못돼도 구현 단계에서 걸러지지 않습니다.

**기획의 결과를 추적하지 않았습니다.** 기능을 정의하고 만들었지만, 그 기능이 의도한 효과를 냈는지 확인하는 지표를 함께 설계하지 않았습니다.

### 어떤 의사결정이 가장 중요했는가

**"결정을 기록으로 남긴다"를 원칙으로 삼은 것**입니다. 혼자 아는 것은 조직에 남지 않습니다. 이 원칙이 이후 백엔드 프로젝트에서 ADR·개발원장으로 이어졌습니다.

### 배운 것

| 관점 | 배운 것 |
|---|---|
| **제품** | 예외 케이스와 데이터 요구사항이 빠진 기획서는 반드시 구현 단계에서 되돌아온다 |
| **협업** | 조사는 도입 기준까지 가야 의사결정에 쓰인다 |
| **조직** | 한 사람이 다 하면 손실은 없지만 검증도 없다: 그래서 기록이 더 중요해진다 |
