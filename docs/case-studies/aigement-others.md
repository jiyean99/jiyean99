# R&D 전수 검토 · 대외 활동 · 팀 운영

> **Case Study**
> 제품을 만드는 일 옆에서 함께 수행한 **검증 · 대외 · 전사 과제**를 묶었습니다.

[`← 경력 상세로`](../experience.md)

---

## A. Executive Summary

에이아이지먼트 재직 3개월 동안 PLYN·정시성 PoC라는 두 주력 옆에서 수행한 부수 과제들입니다. 성격이 서로 다르지만 한 가지가 공통됩니다: **"주장을 그대로 받아쓰지 않는다"**는 것.

가장 비중이 큰 것은 **공급사 탐색 R&D 저장소 전수 검토**입니다. 대외로 나갈 수치를 확정하기 전에 재현 검증이 필요했고, 문서를 읽는 대신 직접 실행해 확인했습니다. 테스트 416개를 clean venv에서 돌리고, 네트워크·키 없이 오프라인 dry-run으로 산출물 생성까지 확인했습니다.

이 과정에서 **제가 발견한 린트 292건이 저장소가 아니라 제 로컬 환경 문제였다는 것을 스스로 규명**했습니다. 그대로 보고했으면 오보였습니다.

# Part 1. 공급사 탐색 R&D 전수 검토

`2026.08` · 사내 R&D 저장소 · 코드/연구 신뢰성 검토

## 01. Problem

```text
현재 상황
  사내 R&D 저장소의 성과를 대외 자료로 정리하는 단계였다

      ↓
문제
  성과 수치의 근거가 저장소 문서에만 있고, 재현 검증을 거치지 않은 상태였다

      ↓
원인
  검증하려면 환경을 세팅하고 실제로 실행해야 하는데, 그 비용이 적지 않다

      ↓
비즈니스 영향
  대외로 나간 수치는 되돌릴 수 없다

      ↓
해결해야 할 핵심 문제
  문서의 서술이 아니라 실행 결과로 1차 신호를 확보한다
```

## 02. 검토 방법 - 저장소의 주장에 의존하지 않는다

| 검증 | 결과 |
|---|---|
| `pytest` (clean venv) | **416개 전부 통과** (2.35초) |
| `ruff check` (CI 기준 select) | All checks passed |
| **오프라인 dry-run** (네트워크·키 없이) | end-to-end 산출물 생성 성공 |
| 추적 파일 시크릿 스캔 | **라이브 키 0건** · `.env.example`만 placeholder |
| 로컬 산출물 대조 | 문서에 적힌 수치를 로컬 산출물로 재현해 대조 |
| 개발 창 커밋 대조 | 개발 기간의 커밋을 전수 확인 |
| 코드 규모 | Python **32,237 LOC** / 112파일 전수 검토 |

**clean venv와 오프라인 dry-run을 고집한 이유** - 내 환경에 이미 깔린 패키지나 남아 있는 API 키 때문에 "돌아가는 것처럼" 보일 수 있습니다. 재현성을 검증하려면 아무것도 없는 상태에서 시작해야 합니다.

## 03. Core Finding - 내가 발견한 숫자를 내가 반증하다

> 🔥 **이 검토에서 가장 값어치 있었던 순간입니다.**

```text
Finding
  로컬에서 ruff check 를 돌리니 292건이 나왔다.
  "코드 품질 문제 292건"으로 보고할 뻔했다.

Verification
  보고 전에 왜 이렇게 많은지 확인.
  프로젝트/CI 가 실제로 쓰는 기본 select 로 다시 실행 → 전부 통과.

Cause
  내 로컬 환경의 비표준 확장 룰셋에 의한 환경 착시였다.

Result
  292건을 "저장소 문제"가 아니라 "내 환경 문제"로 정정.
  그대로 보고했으면 오보였고, 저장소 담당자에게 부당한 지적이 됐을 것이다.
```

**배운 것**: 남의 주장을 의심하는 것보다 **내가 방금 만든 숫자를 의심하는 것**이 더 어렵고 더 중요합니다.

## 04. 검토 범위

ML/LLM 코어 · 데이터 수집 · 인프라 · 테스트/재현성 · 연구 신뢰성 · 개발 위생 여섯 영역을 나눠 평가했습니다.

각 영역마다 **문서의 서술이 아니라 코드에서 확인할 수 있는 신호**를 근거로 삼았습니다: 예를 들어 "근거를 보존한다"는 주장은 실제로 근거 필드가 파이프라인 끝까지 전달되는지, "장애에 강하다"는 주장은 예외 경로가 실제로 폴백을 타는지를 코드 게이트에서 확인했습니다.

> ⚠️ **영역별 평가 등급과 지적 사항은 사내 문서이므로 이 공개 문서에 옮기지 않습니다.**
> 여기서는 검토 방법과, 그 과정에서 제가 배운 것만 정리합니다.

## 05. Result

검토 결과로 **즉시 처리가 필요한 항목 3건을 근거와 함께 제안**했습니다. 조직에 불편할 수 있는 정정이었지만, 실행 로그와 문서 대조를 근거로 붙여 올렸습니다.

> ⚠️ **제안의 구체적 내용은 사내 문서·대외 산출물과 직접 관련되므로 이 공개 문서에서는 다루지 않습니다.**

기술적으로 하나만 일반화해 적으면, **평가 데이터의 독립성** 문제입니다. 모델이 만든 답을 같은 계열 모델이 채점하면 그 계열의 편향이 그대로 통과합니다. 성능이 좋아 보이지만 실제로는 자기 자신을 채점하고 있는 구조라, 이런 순환은 문서에 명시하고 끊어야 합니다.

## 06. Reflection

**잘한 것** - 문서를 읽고 요약하는 대신 직접 실행했습니다. 그리고 내 발견을 스스로 반증했습니다.

**부족한 것** - 검토 대상 저장소는 제가 만든 것이 아니어서, 지적한 항목이 실제로 개선됐는지까지는 확인하지 못했습니다. 그리고 제가 PLYN sourcing 도메인 담당이라 **만드는 사람과 검증하는 사람을 겸한 구조**였습니다. 이런 경우 근거와 재현 절차를 함께 제출하는 것으로 보완했지만, 독립적인 제3자 검토가 더 나았을 것입니다.

# Part 2. PLYN CES 2027 혁신상 출품 · 대외 데모

`2026.06 – 2026.08`

## 01. Problem

기술이 아무리 좋아도 **2분 안에 이해되지 않으면 심사에서 남지 않습니다.** 원안 플롯은 기능을 순서대로 보여주는 구성이었고, 심사자가 "이게 왜 혁신인가"를 스스로 조립해야 했습니다.

## 02. Solution - 2분 안에 이해되고 기억되게

- **플롯 재구성** - 기능 나열이 아니라 문제 → 전환점 → 결과의 서사로 120초를 재배치
- **심사 관점 반영** - 심사 기준에서 무엇이 가점인지를 기준으로 원안 대비 핵심을 변경
- **인터랙티브 리스크 리포트 · 리스크 보드 UI** - 정적 화면이 아니라 조작 가능한 데모로

## 03. Trade-off

> ⚠️ **데모와 제품은 다릅니다.** 전시에서 시연한 **공급사 발굴 AI 챗봇은 데모 산출물이며 제품 코드베이스에 포함되지 않습니다.**
> 이 구분을 흐리면 포트폴리오 전체의 신뢰가 무너지므로, 문서 어디에서도 데모를 제품 기능으로 적지 않았습니다.

## 04. Result

스마트테크 코리아 2026 데모 출품 · PLYN CES 2027 혁신상 출품.

> ⚠️ **수상 결과·심사 평가 등은 이 문서 작성 시점에 확정되지 않았거나 공개할 수 없습니다.**

# Part 3. 팀 협업 체계 · 개발 환경 · 운영

`2026.06 – 2026.08`

## 01. Problem

```text
현재 상황
  업무가 Notion · 메일 · 구두로 흩어져 있고, 개발 환경 셋업이 사람마다 다르다

      ↓
문제
  "지금 뭐가 어디까지 됐나"를 매번 물어봐야 알 수 있다
  새 저장소를 받으면 환경 세팅에서 반나절이 사라진다

      ↓
원인
  협업 비용의 대부분은 "물어봐야 알 수 있는 것"에서 나온다

      ↓
해결해야 할 핵심 문제
  묻지 않아도 보이게 만들고, 환경을 재현 가능하게 만든다
```

## 02. Solution

### 이슈 관리 이관 - 묻지 않아도 보이게

- 흩어져 있던 업무를 **Jira 티켓 체계로 정리·이관**해 추적성과 협업 가시성 확보
- Atlassian 업무 인프라 구성 보고를 작성해 도구 구성·운영 방식을 전사에 공유
- 산출물 배포 형식 이원화 - **깊은 레퍼런스는 MD, 팀 공유는 데크로**

### Slack Git 알림 봇 - 흐름을 화면에 올리기

커밋·PR·배포 이벤트를 Slack으로 자동 알림해, **누가 무엇을 언제 올렸는지 별도 확인 없이 드러나게** 했습니다.

### 개발 환경 온보딩 표준화

| 원칙 | 내용 |
|---|---|
| **멱등 셋업** | 셋업 스크립트를 **재실행 안전**하게 설계 - 몇 번 돌려도 같은 상태 |
| **환경 표를 만든다** | 담당 저장소별 Python 버전 · 패키지 매니저 · 설치 명령 · 필요한 `.env` 키를 표로 정리 |
| **의존성 표준 선언** | Python 의존성을 `uv` + `uv.lock`으로 표준화하고, pip 과도기 프로젝트의 설치 명령 통일 |
| **함정을 문서에 쓴다** | 포트 충돌처럼 실제로 부딪히는 것을 명시 |
| **시크릿은 이름만** | 값이 아니라 **키 이름만 문서화**하는 원칙 수립 |

> 💡 마지막 두 개가 실제로 시간을 아꼈습니다. "포트가 겹칠 수 있다"를 한 줄 적어두면 다음 사람이 30분을 안 씁니다.

### 연구노트 체계 재설계 <sub>(정부지원사업 2차년도)</sub>

연구 기록이 **실제 개발 이력과 1:1로 대응되도록** 작성 체계를 다시 잡았습니다.

```text
원칙   git 커밋 · PR · 설계 문서를 근거로 작성하고, 각 회차에 커밋 해시를 명시
매핑   작업 분류를 실제 작업패키지 기준으로 재정렬
절차   주간 git log 기반으로 상시 작성하도록 프로세스 정의
정직성 근거를 확인할 수 없는 항목은 추정으로 채우지 않고 "확인 필요"로 표시
```

> 💡 마지막 원칙이 핵심입니다. 기록은 **근거가 있을 때만 기록**입니다. 빈칸을 채우면 문서는 완성되지만 아무 정보도 남지 않습니다.

### 클라우드 · 보안 정책 대응

AWS GPU 예약 서비스(EC2 Capacity Blocks for ML) 활용 가이드 검토, IAM User 사용 원칙·계정 탈취 예방 보안 교육 대응, Bastion을 통한 Private GPU 서버 접속 구성.

### 퇴사 인수인계 - 나가는 방식도 일하는 방식이다

업무 자산을 아카이브로 정리하고 매니페스트를 문서화했습니다. **각 아카이브를 4중으로 검증**했습니다.

```text
① 크기          ② 엔트리 카운트
③ 시크릿 · 제3자 패턴 grep
④ 원본과 파일 단위 대조 (유니코드 NFC 정규화)
```

- **시크릿·제3자 개인정보를 의도적으로 제외**하고 그 목록과 사유를 명시
- 남아 있는 개인키·환경변수 실값에 대해 **삭제·키 회전 권고**를 문서로 인계
- **원본은 하나도 삭제하지 않는 원칙**으로 복구 가능성 보장

> ④ 유니코드 NFC 정규화가 중요했습니다. macOS와 Windows의 한글 파일명 정규화가 달라, 정규화 없이 대조하면 같은 파일이 다르게 보입니다.

### 함께 수행한 기타

- **플랫폼 전환 대응** - 저장소·인프라 이식 계획과 인증 설계를 정리한 전환 보고서·실행 핸드북 작성
- **분류 체계 데이터 정비** - eClass 표준 분류 체계 및 국문 매핑 데이터를 품목 분류 도메인의 기준 데이터로 준비
- **조달·구매 데이터 확보** - 조달 데이터와 기업별 Spend 분석 자료를 절감 발굴 로직의 검증 데이터로 정리
- **회의 기록 · 설계 검토** - 플로우/시스템 설계 검토 회의, 전사 미팅, PoC DS 프로세스 공유를 회의록으로 남기고 후속 액션으로 연결

## 03. Result

| 항목 | 내용 |
|---|---|
| 이슈 관리 | 분산 도구 → Jira 단일 체계 이관 |
| 개발 알림 | Slack Git 알림 봇 신설 (커밋 · PR · 배포) |
| 온보딩 | 저장소별 셋업 표준화 · 멱등 스크립트 |
| 연구 기록 | 커밋 해시 기반 실증 기록 체계 |
| 인수인계 | 4중 검증 아카이브 + 키 회전 권고 인계 |

> ⚠️ **정량적 효과(문의 감소·셋업 시간 단축 등)는 측정하지 않았습니다.**

## 04. Reflection

**잘한 것** - 협업 도구를 바꾼 게 아니라 **"물어봐야 알 수 있는 것"을 줄이는 방향**으로 정리했습니다. 도구가 목적이 되면 도구만 늘어납니다.

**연구노트에서 배운 것** - 기록은 근거가 있을 때만 기록입니다. 근거 없는 항목을 "확인 필요"로 남기는 편이, 빈칸을 채워 완성된 것처럼 보이게 하는 것보다 훨씬 쓸모 있는 문서를 만듭니다.

**부족한 것** - 도입한 체계들이 제가 떠난 뒤에도 유지되는지는 확인할 수 없습니다. 사람이 떠나면 사라지는 체계라면 그건 체계가 아니라 습관입니다.
